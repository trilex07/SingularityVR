## Ranked current bottlenecks and call paths

1. **CONFIRMED unnecessary diagnostic work; FIXED in this branch:** `Hook_Draw*` -> `MenuDrawTraceRecord` -> D3D9 render target, shaders, texture, viewport, scissor, render states and VS constants queried synchronously per sampled draw. `MenuDrawTraceFrame` also calls `VrMenuStateToken` and clears a 2048-entry table on transitions. The recorder was default ON. Set default OFF and gate its frame function before token/table work; `[Diagnostic] MenuDrawTrace=1` explicitly restores the old investigation path. This is a bounded transition cost, not proven to be the combat hitch.
2. **LIKELY remaining source of the old 77 FPS window:** draw submission/driver or mod draw-wrapper work when split draws rise. Existing `ShadowTrace` native forwarding timer was designed to split these costs. No comparable current-build event profile shows which side dominates. A 3330 peak is a count, not a CPU duration; no renderer simplification is justified yet.
3. **LIKELY occasional frame waits, not attributed to firing:** render-thread `CaptureBackbufferForXr` issues a D3D9 GPU fence, polls `GetData(..., D3DGETDATA_FLUSH)` with a 100 ms bound, then either copies through the shared D3D9Ex resource or uses blocking `GetRenderTargetData` plus a CPU upload. This is a true synchronous frame path, but historical 1.76–2.27 ms fence averages are not evidence of a combat-specific stall. Altering its ordering risks stereo pose/pixel mismatches.
4. **LIKELY first-use or failure-path costs:** `Log()` normally queues through `AsyncLogEnqueue` (short SRW section), but its fallback opens/appends/closes a file synchronously under `g_lock` when the worker is inactive. `FireAmmunition` and TMD haptic hooks have bounded receipt logs; class/reflection, VFX initialization and native UE3 effect/audio creation can happen on the game thread. No archived per-shot stack or duration identifies any of these as a present hitch. Do not disable gameplay callbacks or effects.
5. **EXCLUDED for repeated held-trigger drops on the accepted cache baseline:** DirectInput helper enumeration (~75–76 ms) and texture classification hash churn were measured, fixed and physically retested. A reappearance would need a new actual enumeration/cache receipt, not a generic FPS report.

## Gameplay producer audit

- **Fire:** `Hook_ProcessEvent` identifies native `FireAmmunition` on the game thread; native UE3 `InstantFire`/`ProjectileFire`, trace, VFX/audio and animation occur inside or downstream of that call. The mod marks the fire event, updates a bounded adaptive-trigger state under `g_shotRunLock` when enabled, and posts VFX data to the render-thread mailbox. The native call duration in PR #71 is wall time, not thread CPU. First use and repeated fire remain distinct hypotheses.
- **Damage:** `TakeDamage` is a native event; gore settings are applied at that boundary when enabled. Particle/decal work may follow on game/render threads. Existing evidence lacks a synchronized hit-to-frame stack, so the gore hook cannot be named the hitch from source alone.
- **Pickup:** a `Use`/Grip edge means *attempted* interaction. Ordinary world-item pickup has no verified success marker in the current probe. WeaponLocker factory acquisition and shoulder-magazine FSM are different producers and must be analyzed separately. No historical ordinary-pickup timing was found.
- **Switch:** `Pawn.Weapon` identity change is a reliable switch marker. `RefreshArmedState` executes once per render frame; positive pawn cache and throttled miss paths protect the GObjects walk. Native weapon construction and first texture/material uploads are not timed by that marker alone.
- **Input:** current event-invalidated DirectInput cache preserves the historically accepted callback replay. `originalPoll` can still enter native input work at context invalidation; known long scans are not a per-shot explanation on the post-cache profile.
